## 1. Problem, Gap & Hypothesis
Developer workstations are a standing software-supply-chain target, and the IDE is the highest-value application on them — per the 2022 Stack Overflow survey (>70k respondents) **VS Code is used by more than 74% of developers** (§I). VS Code is **built on Electron**, which embeds Chromium and Node.js into a standalone desktop app, so "VS Code extensions are similar to Node.js applications": they can import any of npm's million-plus packages, and — **unlike browser extensions — they are not sandboxed**. They have full access to view and modify the VS Code UI and execute with the same privileges as VS Code itself: shell commands, file read/write, outbound network connections, and listening network servers (§I, §II).

The stated gap: "While prior work has extensively studied vulnerabilities in Node.js, npm, JavaScript, and Electron, vulnerabilities in VS Code extensions have been largely unstudied" — only a handful of blog posts had looked at individual extensions (§I). A second, subtler gap is that **off-the-shelf SAST rules do not transfer**: in a VS Code extension, *user* input is inherently trusted, so classic XSS/taint rules fire only false positives; the genuinely untrusted inputs are the ones the IDE threat model creates — files and settings inside a cloned repository, and localhost web servers reachable from the developer's browser (§I). The implicit hypothesis is that once the threat model is re-encoded correctly, real, exploitable code-execution flows will be found at ecosystem scale.
(KO) 핵심 갭 두 가지: (1) VS Code 확장 취약점에 대한 학술 연구가 사실상 전무했고, (2) 기존 SAST/CodeQL 규칙은 "사용자 입력=신뢰"인 IDE 위협 모델과 맞지 않아 그대로 쓰면 오탐만 난다. 그래서 **위협 모델을 먼저 정의하고 그에 맞는 규칙을 새로 작성**하는 것이 이 논문의 방법론적 출발점이다 — Electron 앱마다 위협 모델이 다르다는 본 논문의 함의는 논문 전체에서 재사용 가능한 논리다.

## 2. Methodology
A threat model first, then rules built to match it (§III–§IV):

- **Adversary goal:** steal secrets from, or modify source on, a developer workstation as a supply-chain step. Arbitrary code execution inside an extension is treated as a sufficient precondition; file modification also suffices (write a file that is later executed, e.g. `.bashrc`, or edit the target source directly).
- **Four entry points (taint sources):** (1) **workspace settings** — `.vscode/settings.json` inside a cloned repo, read via `vscode.workspace.getConfiguration`; (2) **file read** — any workspace file read via `fs.readFile`/`readFileSync` or `vscode.workspace.fs.readFile`; (3) **network response** — data returned to `http.get/request`, `axios.get`, `request.get` (on-path attacker over HTTP, or an attacker-influenced URL); (4) **web server** — a localhost server spawned by the extension (`server.listen()`, `express.get()`) that any website open in the developer's browser can reach.
- **Three targets (taint sinks):** shell command, `eval()`, and file write.
- **Implementation:** **12 custom CodeQL taint-analysis rules**. CodeQL ships no VS Code API classes, so the authors define their own (e.g. `VSCodeWorkspaceConfig`, which resolves the imported `vscode` module and matches `getConfiguration` calls through the AST; `UntrustedURL`, which unions file reads, client-request responses, route-handler requests and workspace config as sources). Built-in classes (`FileSystemReadAccess`, `Http::RouteHandler`, …) are reused where they fit.
- **Automated filters + manual triage:** files inside the extension's own directory are treated as trusted (developers are assumed non-malicious); `eval()` results whose string is bracket-enclosed are dropped; file-write flows are kept only when *both* path and content are attacker-influenced; network flows are narrowed to insecure URLs. CodeQL cannot do constant propagation over composed path strings, so file-path trustedness is settled by manual inspection — the authors report needing to look at "3 to 4 nodes" on the data-flow path, "typically less than a minute" per node.
- **Exploit verification:** PoCs are written by hand, prioritizing high-install and non-obfuscated extensions, because PoC development is "time and labor intensive."

**Assumptions (explicit, §III):** extension developers are not malicious; users are not attacking themselves; **the user has disabled VS Code's Restricted Mode** after cloning an untrusted repo; files outside the workspace are trusted.
(KO) 방법론의 교훈: *도구 자체는 CodeQL이라는 기성품*이고, 기여의 본질은 **위협 모델 → source/sink 정의 → 규칙 인코딩 → 수동 PoC 검증**의 파이프라인이다. 자동 필터로 못 거르는 부분(경로 문자열 상수 전파)은 정직하게 수동 검사로 처리했다고 명시. Restricted Mode 해제를 가정한다는 점은 위협 모델의 실질적 약점이자 인용 시 반드시 같이 적어야 할 조건.

## 3. Experiments / Evaluation Setup — targets, dataset sizes, configs, what was measured
- **Target:** the Microsoft Visual Studio Marketplace, scraped **January 2023**. Metadata collected: extensionName, publisherName, lastUpdated, installs, GitHub repo; plus GitHub repo content and npm advisory data from Open Source Insights.
- **Dataset funnel:** **43,436** extensions on the marketplace → **25,402** contained JavaScript/TypeScript code (the analysis set); the remaining **18,034** were code-free (themes, snippets).
- **Dataset characterization:** **40%** of extensions had not been updated in >2 years, though **54%** of installations belong to extensions updated within 3 months (18% of installs are on extensions untouched for 2 years). **80%** of extensions have fewer than 5 direct dependencies, but transitive data (recoverable for **15,185** extensions that shipped a lock file) shows **13,655** with **>100 transitive dependencies**, and **9,710 of 15,185 (63.9%)** import a package carrying a **critical-level npm advisory**.
- **Capability baseline (Node.js resource access, measured with CodeQL):** **5,112** extensions access files, **4,074** access the network, **1,902** call shell-command APIs, **322** spawn a local web server — and of those 322, the authors installed and activated the extensions and **verified 65** that opened a socket immediately on activation.
- **What was measured:** for each of the 12 source→sink pairs, a funnel from "extensions containing both source and sink" → raw CodeQL flows → post-filter flows → manually investigated → verified PoC / not exploitable / unable to confirm (Tables III–VI). Investigation was sampled by install count (thresholds of >40,000 installs for the workspace-settings→shell case, >5,000 for the file-read cases).
(KO) 데이터셋 깔때기: 43,436 → 25,402(코드 포함). 조사 대상은 설치 수 기준으로 샘플링했으므로 **21건은 하한(lower bound)** 이다. 의존성 수치(9,710/15,185 = 63.9%가 critical 권고 패키지 포함)는 "Electron 앱의 확장 계층이 npm 공급망을 그대로 상속한다"는 주장을 뒷받침하는 데 매우 인용하기 좋다.

## 4. Results / Key Findings — concrete numbers
**Headline: 21 extensions with verified proof-of-concept code-injection exploits, totalling over 6 million installations** (abstract, §I). Broken out by source→sink from §VI:

| Source → Sink | Both present | CodeQL flows | After filters | Investigated | **Verified PoC** | Installs of PoC set |
|---|---|---|---|---|---|---|
| Workspace settings → shell | 2,213 | 389 (~18%) | 389 | 27 (>40k installs) | **7** | >5.7M |
| Workspace settings → `eval()` | 192 | 12 | 12 | 12 | **6** | >80,000 |
| Workspace settings → file write | 1,847 | 79 | 24 | 24 | 0 | — |
| File read → shell | 1,718 | 75 | 75 | 26 (>5k installs) | **4** | >121,000 |
| File read → `eval()` | 397 | 55 | 34 | 34 | **4** | >11,000 |
| File read → file write | 2,847 | 1,296 | 150 | 21 | 0 | — |
| Network response → shell | 174 | **0** | 0 | 0 | 0 | — |
| Network response → `eval()` | 122 | 19 | 1 | 1 | 0 | — |
| Network response → file write | 259 | 191 | 25 | 25 | 0 | — |
| Web server → shell | 151 | 3 | 3 | 3 | 0 | — |
| Web server → `eval()` | 64 | **0** | 0 | 0 | 0 | — |
| Web server → file write | 146 | 6 | 3 | 3 | **1\*** | >279,000 |

\* partial **file-integrity** attack, not code injection (Azure Data Lake Tools). 7 + 6 + 4 + 4 = **21** code-injection PoCs.

- **Where the risk actually is:** workspace settings and workspace files are by far the most productive sources; **shell command and `eval()` account for the large majority of verified code execution** (§VII). Network responses and local web servers produced almost nothing exploitable.
- **Named case studies (all verified):** **git-graph** (5.1M installs) — `git.path` workspace setting flows to `child_process.spawn`, so a repo shipping `{"git": {"path": "a-shell-script.sh"}}` executes on workspace open; **Django Commands** (49k) — `python.pythonPath` setting into `cp.exec`; **scss-lint** (62k+) — `scssLint.statusBarText` setting straight into `eval()`; **CMake Test Explorer** (76k+) — content of a workspace `CMakeCache.txt` into `spawn()`; **autodocblocker** (10k+) — `eval(fs.readFileSync('.autodocblocker.js'))`; **Azure Data Lake Tools** (279k+) — local Express endpoint `/api/editScript` writes attacker-supplied content to an attacker-named file.
- **Ecosystem hygiene findings:** **5 extensions call Heroku URLs, 4 of them pointing at *deleted* Heroku apps** whose subdomains anyone can re-register (e.g. `flask-apillist.herokuapp.com`) — a live supply-chain takeover primitive. **Code cloning:** 10 extensions shared near-identical vulnerable code; of the 45 pairwise Moss comparisons, **28 returned ≥90% matched lines** in at least one directory and all 45 matched ≥40%, showing how one vulnerable pattern propagates across the marketplace.
- **Disclosure:** all affected developers notified; **6 confirmed**, **3 released fixes**; GitHub Security Team and the Microsoft VS Code team also notified.
- **Stated limitations (§VII):** CodeQL misses unconventional coding patterns; **dependency source code was excluded** (the study is about extensions, not npm packages) even though vulnerabilities there would still reach users; static analysis yields false positives, mitigated by filters and PoCs; PoC verification was sampled, not exhaustive.
(KO) 인용 시 가장 강한 숫자: **21개 확장 / 600만+ 설치**, git-graph 단독 510만 설치. 반대로 "network response → shell 조합은 flow 0건"처럼 **아무것도 안 나온 칸**도 중요하다 — 공격면이 균일하지 않고 *워크스페이스 설정·파일*에 집중된다는 증거다. 21건은 설치 수 상위 샘플만 수동 검증한 결과이므로 실제 규모의 하한.

## 5. How to cite in Related Work
> Closest to our setting, Lin et al. studied the extension ecosystem of Visual Studio Code — itself an Electron application embedding Chromium and Node.js — and showed that third-party extensions constitute a code-execution attack surface on developer workstations [UntrustIDE, NDSS'24]. Because extensions are unsandboxed and run with the full privileges of the host application, they encoded a VS Code-specific threat model as twelve CodeQL taint rules over four untrusted sources (workspace settings, workspace files, network responses, and locally spawned web servers) and three sinks (shell command, `eval()`, file write), and applied them to the 25,402 code-bearing extensions of the marketplace. Manual verification yielded proof-of-concept code-injection exploits in 21 extensions with more than six million combined installations, with workspace settings and workspace files responsible for every verified case. Their study, however, treats the extension as an ordinary Node.js program: the analysis stops at the extension-host boundary and does not model the Electron mechanisms — renderer/main separation, preload and `contextBridge`, or IPC channel validation — through which an attacker inside the renderer would otherwise reach the same sinks.

(KO) 이 논문이 학위논문에서 갖는 위치:
- **동기(motivation)로 가장 강력하다.** "Electron 앱은 이론적으로 위험하다"가 아니라 "개발자 74%가 쓰는 실제 Electron 앱에서 600만 설치 규모의 검증된 RCE PoC가 나왔다"는 구체적 근거다. Inspectron(오설정 카운트, 익스플로잇 미증명)과 대비해 **검증된 익스플로잇**을 제시한다는 점이 차별적이며, "오설정 통계 → 실제 익스플로잇"으로 서사를 이어붙이기 좋다.
- **동시에 명확한 갭을 남긴다.** 분석 대상은 **확장 호스트(Node.js) 내부의 taint 흐름**이며, Electron 고유의 공격면 — 렌더러↔메인 IPC, preload/contextBridge 경계, `nodeIntegration`/`contextIsolation` 설정, 커스텀 프로토콜/딥링크 — 은 전혀 다루지 않는다. 즉 **"Electron 앱 하나(VS Code)의 확장 계층"** 에 대한 연구이지 **"Electron 프레임워크 계층"** 연구가 아니다. 학위논문은 여기서 두 방향으로 확장 가능: (a) 단일 앱 → 다수 Electron 앱으로의 일반화, (b) 확장 호스트 → 프로세스 경계(IPC/preload)로의 확장.
- **방법론적으로 대비축이 된다.** UntrustIDE = **정적(CodeQL) + 수동 PoC**. 반대편에 Inspectron = **동적 블랙박스 + 익스플로잇 미증명**, Buzz to Boom(arXiv'26) = **동적 분절 퍼징 + 자동 end-to-end 익스플로잇 합성**. "정적은 흐름을 넓게 찾지만 익스플로잇 확인이 수작업 병목이다"라는 문장을 쓸 때 근거로 삼기 딱 좋다(본 논문 스스로 "PoC 개발은 시간·노동 집약적"이라 인정).
- **위협 모델 설계의 선례.** "앱마다 무엇이 untrusted인지 다시 정의해야 한다(사용자 입력은 신뢰, 저장소 파일은 불신)"는 통찰은 다른 Electron 앱으로 방법을 옮길 때 그대로 재사용할 수 있는 프레임이다.
- **계보(lineage).** 저자 중 Koishybayev·Kapravelos는 이미 ledger에 있는 **Mininode(RAID'20)** 의 저자다 → NCSU(Enck/Kapravelos) 라인의 Node.js 공격면 축소 연구가 IDE/Electron 앱 계층으로 확장된 결과로 배치할 수 있다.

## 6. Caveats / what I could not confirm from the text
- **Tables III–VI were read as flattened PDF text**; the column headers ("Filters", "Investigated", "PoC", "Not Exploitable", "Unable to Confirm" and their sub-columns) run together in extraction. Every number in my table above is corroborated by the explicit prose in §VI-A–D, but before quoting the *per-category* breakdowns (obfuscated / deprecated / activation error / other) verify against the typeset PDF.
- The **file-read → file write** row shows 1,296 raw flows reduced to 150 then 21 investigated with 0 PoCs; the prose lists "one obfuscated, 2 deprecated, one was obfuscated, 6 hard-coded filename, 4 read from extension files, one activation failure, one unconfirmed" — the two "obfuscated" mentions appear to be a duplication in the paper's own text and the categories do not sum cleanly to 21. Do not quote that breakdown.
- The paper reports **21 verified PoCs / >6M installations** in the abstract; the per-row install figures (>5.7M + >80k + >121k + >11k) are stated separately in prose and the paper never states a de-duplicated total, so ">6 million" should be cited as the paper's own aggregate rather than recomputed.
- **Nothing in the paper measures Electron-framework mechanisms.** "Electron" appears only as background (§I, §II) — there is no analysis of `nodeIntegration`, `contextIsolation`, preload, `contextBridge`, renderer↔main IPC, or the Electron sandbox. The PRIMARY tag here reflects that the *target* is a real Electron desktop application and the *task* is vulnerability discovery with verified exploits; the Electron-framework framing in §5 is mine, not the authors'.
- The **Restricted Mode disabled** assumption is load-bearing: with Workspace Trust in restricted mode most of these flows would not execute. The paper argues restricted mode "defeats the purpose of installing extensions," but does not measure how many users actually run with it enabled — I could not confirm any such number.
- **Appendix / Table VII** (CodeQL data-flow counts, database-loading walkthrough) was not read line-by-line.
- No artifact-evaluation badge is stated in the text I read; the CodeQL rules are said to be public at `github.com/s3c2/UntrustIDE` (repository not fetched or verified this run).
