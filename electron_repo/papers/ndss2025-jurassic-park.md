# Welcome to Jurassic Park: A Comprehensive Study of Security Risks in Deno and its Ecosystem

**Authors:** Abdullah AlHamdan, Cristian-Alexandru Staicu (both CISPA Helmholtz Center for Information Security)
**Venue / Year:** Network and Distributed System Security Symposium (NDSS 2025), 23–28 February 2025, San Diego, CA
**Links:** [DOI 10.14722/ndss.2025.23284](https://dx.doi.org/10.14722/ndss.2025.23284) · [author-hosted PDF](https://www.staicu.org/publications/ndss2025.pdf) · ISBN 979-8-9894372-8-3
**Scope tag:** ADJACENT

**Relation to a thesis on discovering Electron-app vulnerabilities (one line):** The best available worked example of *attacking a JavaScript runtime's permission model rather than its code* — coarse-grained permissions that implicitly grant others ("shadow permissions"), paths exempted from checks, and TOCTOU-style indirection — which is precisely the analysis one wants to run against Electron's `webPreferences` / `sandbox` / `contextIsolation` configuration surface.

> **한 줄 요약 (KO):** "기본이 안전하다"고 광고하는 Deno 런타임의 권한 시스템을 정면으로 감사해, 굵은 입자 권한이 다른 권한을 암묵적으로 내포하는 **shadow permission**, 권한 검사에서 아예 면제된 **static import**, 심볼릭 링크로 세분화 권한을 무력화하는 결함을 찾아내고 CVE 2건과 런타임 import 메커니즘 재설계를 이끌어냈다.

## 1. Problem, Gap & Hypothesis

**Problem.** Node.js + npm are the canonical insecure server-side JavaScript stack — vulnerability-ridden and a proven supply-chain-attack vehicle. Deno is the "learned from those mistakes" successor: written in **Rust** (memory-safe), **secure by default** (no permission granted unless asked for), a **permission system** gating every sensitive API either statically (CLI flags) or at runtime (prompts), and a **decentralised supply chain** in which dependencies are plain URLs rather than a central registry. Deno's own documentation claims one can "run untrusted code with confidence", like a browser. At the time of study Deno was the second most-used server-side JS runtime (11.2% of developers in State of JS 2022, up from 5.6% in 2021) with ~93k GitHub stars.

**Gap.** Nobody had checked whether the claim holds. Two questions are open: (i) does the *runtime* actually enforce what its permission model promises, and (ii) does the *ecosystem* (deno.land) use the model in a way that preserves any benefit?

**Hypothesis (implicit).** A permission system is only as strong as (a) the completeness of its check placement, (b) the granularity of its permission vocabulary, and (c) the fidelity of the name→resource binding it enforces. Failures in any of the three collapse "secure by default" into ambient authority. All three turn out to fail.

> **(KO)** 이 논문의 문제 설정이 Electron 논문에 그대로 이식된다. Electron도 "`contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`면 안전하다"는 **기본값 서사**를 갖고 있다. 이 논문은 그 서사를 (a) 검사 누락 (b) 권한 입자도 (c) 이름↔자원 바인딩의 충실도 — 세 축으로 분해해 공격하는 방법을 보여준다.

## 2. Methodology

Three distinct methods, in sequence:

1. **Systematic attack-surface transfer (§II-B).** They surveyed **10 years (2014–2024) of top-tier security and software-engineering proceedings** for papers on Node.js-specific security problems, and for *each known issue* attempted to implement a proof-of-concept payload against Deno, recording whether Deno is affected and to what degree the permission system mitigates it (Table I). This is a reusable technique: take an established vulnerability taxonomy for platform A and empirically re-test it on platform B.
2. **Manual security analysis of the permission system (§III),** organised as three failure classes — missing checks, coarse-grained permission implications, and fine-grained enforcement failures — each demonstrated with a working PoC.
3. **Ecosystem measurement of deno.land (§IV).** Crawl all packages via deno.land's official stateless API, download the latest version of each plus its transitive dependencies (snapshot **25 November 2022**), resolve every `import` URL with `deno info URL` to build the dependency graph, and then **monitor the observed URLs' availability for several months**. Permissions were inferred two ways in parallel: from **documentation** (Deno CLI flags in the package README) and from **static analysis of the package code** (calls to privileged APIs), each computed both package-only and including transitive dependencies.

> **(KO)** 방법론에서 배울 점: **①의 "기존 취약점 분류를 새 플랫폼에 하나씩 재현해보기"** 는 Electron 논문 도입부에 거의 그대로 쓸 수 있는 설계다(Node.js 취약점 목록 → Electron 렌더러/메인에서 재현 여부 표). **③의 "문서에 적힌 권한 vs. 코드가 실제로 요구하는 권한"의 이중 추정**도 유용하다 — Electron이라면 "앱이 선언한 `webPreferences` vs. preload가 실제로 노출한 능력"의 격차로 번역된다.

## 3. Experiments / Evaluation Setup

- **Runtime analysis targets:** Deno's permission flags — `--allow-read`, `--allow-write`, `--allow-net`, `--allow-env`, `--allow-sys`, `--allow-run`, `--allow-ffi`, `--allow-hrtime`, `--allow-all` — and the static-import module graph. Deno 1.x (a specific SECURITY.md reference points at v1.18.2 era docs).
- **Ecosystem dataset:** **5,400 packages** from deno.land with associated GitHub repositories, crawled with Puppeteer + GitHub's official JS package; snapshot 25 Nov 2022; URL availability monitored across months into late 2023.
- **Dependency-graph scale:** **20 distinct delivery domains** observed while resolving transitive dependencies (Table II) — deno.land 10,892 URLs (85.15%), esm.sh 904 (7.07%), cdn.skypack.dev 214 (1.67%), cdn.jsdelivr.net 148, raw.githubusercontent.com 125, jspm.dev 81, x.nest.land 51, unpkg.com 49, dev.jspm.io 46, denopkg.com 35, ghuc.cc 32, cdn.esm.sh 22, gist.githubusercontent.com 15, cdn.pika.dev 14, lib.deno.dev 10, cdn.pagic.org 10, crux.land 9, cdn.shopstic.com 8, x.lcas.dev 2, ghc.deno.dev 2, cdn.dreg.dev 1. Illustrative case: importing `earthstar` triggers **114 network requests across 4 domains** to fetch transitive dependencies.
- **What was measured:** whether each known Node.js attack class reproduces on Deno; which coarse permissions implicitly grant which others; per-domain URL and dependent counts; transport protocol (HTTP vs HTTPS) per package; URL availability over time; and per-permission package counts under both inference methods, package-only and transitive (Table III).

## 4. Results / Key Findings

**§II-B — attack-surface transfer.** Most known Node.js security issues **still affect Deno**. Genuine wins: no install phase ⇒ **no install-time hooks**, removing a notorious supply-chain vector; Rust removes most binding-layer memory bugs (though the underlying JS engine can still have them). Partial: **prototype pollution is only half-mitigated** — `Object.prototype.__proto__` is blocked but `Object.prototype.constructor.prototype` is not, merely made harder (it requires polluting three nested property accesses simultaneously). Unmitigated: **ReDoS**; no provenance control on `eval` (no CSP-`script-src` analogue); no confinement of untrusted dependencies' effect on trusted code; WebAssembly/low-level bugs spill into the runtime unchecked.

**§III-A — checks that are simply absent.** **Static `import` statements are exempted from permission checks entirely** — by design, per Deno's security model: the initial static module graph built by `deno run` carries no permission restrictions. Consequences the authors demonstrate: a **tracking-pixel import** (URL GET parameters carry a per-victim unique ID, telling the attacker exactly when the developer runs the app — "when do they open their IDE or their crypto wallet"); and, given `--allow-write` on the current folder, a **metamorphic exfiltration attack** — the payload reads a sensitive file, appends it as a GET parameter to an attacker URL, and rewrites *itself* to contain that import, so the **second** run exfiltrates the data over the network **although network permission was never granted**.

**§III-B — shadow permissions (the paper's most transferable concept).** Deno's docs warn that `--allow-run` and `--allow-ffi` escape the sandbox. The authors show that ordinary-looking permissions do too, and map the full implication graph (Fig. 3, distinguishing previously-documented from newly-discovered edges):
- **`--allow-write` ≈ full bypass of the permission system.** Unrestricted write to anything the OS user can write: modify `.bashrc` to inject commands executed outside Deno's sandbox on next login; overwrite executables such as `firefox.exe`. The authors contrast this with Android, which layers additional access control over sensitive OS files.
- **`--allow-read` implicitly grants `--allow-env` and `--allow-sys`**, via the filesystem: `Deno.readTextFile("/proc/self/environ")` ≡ `Deno.env.toObject()`; `Deno.readTextFile("/proc/meminfo")` ≡ `Deno.systemMemoryInfo()`.

**§III-C — fine-grained enforcement failures (name→resource indirection).**
- **DNS**: grant network permission for an attacker-controlled domain, then have it resolve to internal IPs ⇒ local-network scanning without permission for those hosts.
- **PATH**: fine-grained `--allow-run=cat` plus write permission ⇒ drop a malicious `cat` on `PATH` and hijack it.
- **Symbolic links (their own finding)**: Deno treats everything reachable *through* a symlink inside a permitted folder as part of that folder. A malicious repo ships `cache/root-folder → /`; the README tells the user to run with `--allow-read=./cache --allow-write=./cache`; the code then reads or writes **any file on disk**, converting fine-grained permissions into coarse ones — which by §III-B means arbitrary command execution.

**§IV — ecosystem.**
- **Transport:** **39 packages** are fetched over plain **HTTP** vs **4,686** over HTTPS — MitM code injection, and it propagates transitively (`outdent` → `litre`/`ultra` → `mesozoic`).
- **Domain takeover:** **2 of the 20 domains are permanently unavailable**, and **one has been for sale cheaply since early February 2023**. It hosts three packages (`denopack`, `deno-react-minimal-frontend`, `deno-react-minimal-fullstack`) reaching **12 more via transitive dependencies**. In response to disclosure **the Deno team bought the domain**. The authors also contacted the affected package maintainers directly; **none responded**.
- **Availability decay:** median **220 unavailable links**, directly breaking **380 packages** and, transitively, **462 more**. Worst observed day, **23 September 2023**: **283 unavailable URLs → 1,332 unavailable packages** (59.44% of that day's unavailable URLs traced to a single CDN); a comparable event at **276 URLs → 1,015 packages**. **21 permanently broken URLs point at Deno's own standard library `std`.**
- **Declared vs. actually-required permissions (Table III).** The documentation/code gap is stark. `--allow-read`: **409** packages document it, **1,491** need it by code analysis; transitively **491** vs **2,743**. `--allow-write`: **246** documented / **1,031** by code (transitively **283** / **2,729**). `--allow-run`: **148** / **532** (transitively **178** / **2,713**). `--allow-net`: **385** / **237** (transitively **488** / **2,714**). `--allow-ffi`: **16** documented, **42** by code, **0** fine-grained; transitively **75** / **139**. `--allow-all` is documented by **33** packages (**39** transitively). Fine-grained variants are rare everywhere (e.g. 36 packages use fine-grained read vs 409 coarse). Worked example of the resulting usability failure: the `open` package documents nothing; `--allow-run` suffices on Windows but on Linux it additionally needs `--allow-read` because of `is_wsl` — which *does* document that requirement, but the requirement is **not propagated up the dependency chain**.

**Disclosure outcome (§V-A).** Reported to Deno's security team in early 2023; after an initially positive exchange **the team stopped responding**. The authors went through a third-party disclosure company at the end of 2023, which reproduced the issues and issued **CVE-2024-21487 (HIGH, symbolic-link findings)** and **CVE-2024-21486 (MODERATE, static-import issue)**. Deno then engaged, promising to **restrict unprivileged static imports to a list of trusted domains in Deno 2.0** and buying the vulnerable domain. Recommendations: import permissions, filesystem-level access control (a blocklist of sensitive paths), compartmentalisation support, and a **manifest file that persists fine-grained permissions**.

> **(KO)** 이 논문에서 학위논문으로 가져올 개념은 단연 **shadow permission**이다. "권한 A를 주면 사실상 권한 B도 준 것"이라는 함의 그래프를 그려서, 문서화된 간선과 새로 발견한 간선을 구분해 제시하는 형식 자체가 재사용 가능하다. Electron 버전으로 옮기면: `nodeIntegration: false`인데 preload가 `child_process`를 감싸 노출하면? `sandbox: true`인데 `contextBridge`로 파일 읽기 함수를 노출하면? `--allow-write ≈ 전체 우회`와 정확히 같은 구조다. 두 번째로 가져올 것은 **"문서에 선언된 권한 vs. 코드가 실제로 요구하는 권한"의 정량적 격차**(409 vs 1,491)이며, Electron에서는 "앱이 켠 보안 옵션 vs. preload가 실제로 뚫어놓은 구멍"으로 번역된다.

## 5. How to cite in Related Work

> Permission-based confinement has been proposed as the answer to JavaScript supply-chain risk, but recent evidence suggests the guarantee is weaker than advertised. AlHamdan and Staicu [ref] audit Deno — a runtime marketed as secure-by-default, written in Rust and gating every sensitive API behind an explicit permission — and show that the model degrades to ambient authority in three independent ways: static `import` statements are exempt from permission checks altogether, enabling network exfiltration without network permission; coarse-grained permissions carry undocumented *shadow permissions* (a granted write permission is effectively a full bypass, and a granted read permission subsumes the environment and system-information permissions via `/proc`); and fine-grained permissions fail to bind names to resources, so a symbolic link planted inside a permitted directory silently escalates directory-scoped access to whole-filesystem access. Their measurement of 5,400 deno.land packages further shows that developers document far fewer permissions than their code requires (409 packages document filesystem read; 1,491 require it), and that the decentralised URL-based supply chain introduces domain-takeover and availability failures absent from centralised registries. Two CVEs and a redesign of Deno's import mechanism followed. Electron poses the same question in a desktop setting — its `webPreferences` flags (`sandbox`, `contextIsolation`, `nodeIntegration`) constitute a permission model whose enforcement is likewise mediated by application-supplied preload code — but no comparable systematic audit of that model's enforcement gaps exists.

> **(KO)** 포지셔닝 정리. 이 논문은 **방어 기법 제안이 아니라 "선언된 보안 모델과 실제 시행 사이의 간극"을 파는 감사(audit) 논문**이며, 그래서 본 학위논문과 장르가 같다 — 대조군이 아니라 **본보기**로 인용하는 편이 낫다.
> - **동기 부여**: "secure by default"라는 문구는 검증 대상이지 전제가 아니다. Deno가 그랬듯 Electron의 기본값 서사도 검증되어야 한다.
> - **남긴 빈틈(= 본 논문의 자리)**: ① 대상이 **서버·CLI 런타임**이고 **데스크톱 앱**이 아니다 — 사용자에게 UI가 있고, 웹 콘텐츠를 렌더링하며, renderer↔main 프로세스 경계가 있는 환경은 다루지 않는다. ② 분석이 **거의 전적으로 수동**이다(PoC를 손으로 작성). 자동 탐지 도구가 없다 — 본 논문이 자동화를 제안한다면 명확한 델타가 된다. ③ Deno의 권한은 **CLI 플래그로 사용자가 부여**하지만, Electron의 권한은 **개발자가 코드에 박아두고 사용자는 볼 수 없다** — 즉 Electron 쪽이 더 나쁘며, "사용자 동의"라는 완화 수단조차 없다는 논거로 쓸 수 있다. ④ 저자들이 권고한 **"세분화 권한을 담은 매니페스트 파일"** 은 Electron에 아직 존재하지 않는 것이다.
> - **주의**: 이 논문은 Deno 전용이므로, Related Work에서 Electron과 나란히 놓을 때는 "JS 런타임 권한 모델 감사"라는 상위 범주로 묶어서 인용해야 자연스럽다. 같은 이유로 이 레저(ledger)의 **Cage4Deno(AsiaCCS'23)는 제외**되어 있다 — 그쪽은 Deno 서브프로세스 전용 *방어* 기법인 반면, 이 논문은 권한 모델 자체에 대한 *공격/감사* 이며 프로토타입 오염·ReDoS·네이티브 확장 경계까지 건드린다.

- **Table I** — the attack-surface matrix mapping each known Node.js issue to "affects Deno / mitigated by permissions" — **renders as symbols in the text extraction and could not be read row by row.** The §II-B prose summary is what §4 above reports. **Do not cite a specific row of Table I from this note.**
- **Fig. 3's exact edge set** (which permission implies which, and which edges are new vs. previously documented) is an image; only the two implications spelled out in prose (`--allow-write` ⇒ effective bypass; `--allow-read` ⇒ `--allow-env`, `--allow-sys`) are grounded here. The figure caption confirms solid = documented, dashed = discovered by the authors.
- **Fig. 7** (URL availability over time) is an image; the availability numbers above come from the surrounding prose, not from reading the plot.
- The **`--allow-net` row of Table III is the one place where documentation exceeds code analysis** (385 documented vs 237 by code). The paper's prose does not explain that inversion in the part I read; likely an artifact of static analysis missing network calls buried in dependencies, but **this is my inference, not the paper's claim.**
- The Deno version(s) against which the PoCs were validated are not stated in the sections I read (a footnote references the v1.18.2-era SECURITY.md). The paper predates Deno 2.0, and the promised import restriction landed in 2.0 — **so the static-import finding is fixed in current Deno**; check current behaviour before presenting it as live.
- **No Electron, CEF, or desktop-application content anywhere in the paper.** Every mapping onto Electron in §5 is mine.
