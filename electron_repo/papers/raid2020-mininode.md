# Mininode: Reducing the Attack Surface of Node.js Applications
**Authors:** Igibek Koishybayev; Alexandros Kapravelos (North Carolina State University)
**Venue / Year:** RAID 2020 (23rd Intl. Symposium on Research in Attacks, Intrusions and Defenses), pp. 121–134
**Links:** [paper](https://www.usenix.org/conference/raid2020/presentation/koishybayev) · [PDF](https://www.usenix.org/system/files/raid20-koishybayev.pdf)
**Scope tag:** ADJACENT
**Relation to a thesis on discovering Electron-app vulnerabilities (one line):** Electron's main process *is* a Node.js runtime, so Mininode's static debloating of unused npm code and its built-in-module (`fs`/`net`) whitelisting directly characterize the supply-chain / attack-surface dimension of the same Node substrate an Electron-vuln thesis must reason about — but it is a *mitigation/measurement* tool for server-side Node, not a vulnerability-discovery technique and not Electron-aware.

> **한 줄 요약 (KO):** Mininode는 정적 분석으로 Node.js 앱의 미사용 코드/의존성을 제거하고 `fs`·`net` 같은 내장 모듈 접근을 화이트리스트로 차단해 공격 표면을 줄이는 도구다. Electron 메인 프로세스가 Node.js 위에서 동작하므로 인접 연구이지만, 취약점 "발견"이 아니라 "축소·측정"에 초점을 둔다.

## 1. Problem, Gap & Hypothesis
Node.js apps are assembled from huge transitive npm dependency trees. The authors' measurement finds that on average only **6.8%** of an application's logical lines of code (LLOC) is original — i.e. **93.2%** is third-party code (§1, §7.2). This bloat carries security risk: untrusted/maintained dependencies, typosquatting and backdoor/ownership-takeover supply-chain attacks, and large unused code that needlessly expands what an attacker can reach. The paper frames the **gap** explicitly: prior Node.js security work focused on the runtime/event-loop architecture and on *why* developers use trivial dependencies and the implications of doing so, but "no research on an attack surface that extensive usage of third-party libraries may bring and ways of reducing [it] … was conducted before" (§1).

**Threat model / hypothesis (§3):** assume an app is *exploitable* (e.g. injection without full arbitrary execution). The hypothesis is that you can (1) *reduce attacker capability* by restricting which built-in modules can load (removing whole capability classes like filesystem or networking when unused) and (2) *block chained exploitation* by removing unused — including unused-but-vulnerable — dependencies, even ones pulled in only as transitive deps. A worked example (Listing 3) shows an attacker abusing `fs.linkSync` to symlink-swap a package's entry point and load an otherwise-unused module via `require`; built-in modules can't be swapped this way because they live in the Node binary.

> **(KO) 코멘트:** 핵심 가설은 "이미 취약한 앱"을 전제로, 미사용 코드/모듈과 내장 모듈 접근을 줄이면 *연쇄(chained) 익스플로잇*의 위력을 떨어뜨릴 수 있다는 것. 즉 초기 취약점 자체를 막는 게 아니라 사후 권한 확대를 차단하는 방어적 관점이다.

## 2. Methodology
Mininode is a static-analysis CLI tool (esprima-based AST parsing) that builds a **dependency graph starting from the entry point** (`package.json`'s `main` field, else `index.js`) and removes whatever is unreachable. Pipeline of five stages (Figure 1): **(1) Parser** → ASTs for every JS file; **(2) Value-binding** → collects per-module metadata (aliases of the `exports` object and `require` function, an identifier→value dictionary to resolve dynamic imports, plus LLOC/stats); **(3) Load Dependency Builder** → file-level dependency graph by resolving `require` arguments (Node's default resolution for string literals; the identifier dictionary for some dynamic imports); **(4) Call Graph Builder** → runs only in fine-grain mode, marks unused exports/functions/variables per module; **(5) Reducer** → deletes unused files / functions.

Two **reduction modes** (the paper's central design lever):
- **Coarse-grained** = file/module-level reduction (drop whole unused files); more reliable because it never tries to remove functions *inside* a used module.
- **Fine-grained** = function-level reduction (also strips unused functions/exports within a module); more aggressive but can over-reduce and break behavior.

A separate mechanism: the authors built a **custom Node.js** that patches the C++-level `require` to enforce a **whitelist of built-in modules** generated by Mininode (generated once and kept fixed; if no whitelist exists, all built-ins are allowed to avoid breakage) (§6.1). Because static analysis cannot soundly handle dynamic code, if Mininode hits a non-resolvable dynamic import (or `eval`) it **aborts rather than risk an unsafe reduction** (§6.3; the GitHub tool reports `DYNAMIC_BEHAVIOUR_DETECTED`).

> **(KO) 코멘트:** 방법론은 "엔트리포인트에서 도달 가능한 코드만 남기는" 정적 도달성 분석. coarse=파일 단위, fine=함수 단위. 동적 임포트/`eval`을 만나면 무리하게 줄이지 않고 중단하는 보수적 설계가 정확성(correctness) 목표를 뒷받침한다.

## 3. Experiments / Evaluation Setup
Two experiments (§7):

**(A) Reduction validation (correctness + effectiveness).** Goal: confirm reduction doesn't break behavior, measured by whether packages' **original unit tests** still pass after reduction. Starting from **1,055,131** npm package names, 225,449 depended on the `nyc`/istanbul test tooling; 49,535 installed and passed tests *before* reduction; after a symlink-based scheme to test the production version and removing failures, **45,045** remained; 6,579 hit unresolvable dynamic imports and ~2.7% threw runtime errors (e.g. heap OOM), leaving a final validation set of **37,242 packages**. Both coarse and fine modes were run and unit-tested.

**(B) NPM-wide attack-surface measurement.** The full list of **1,055,131** npm package names (via `all-the-package-names`, as of 19 Sept 2019) was installed (production version) and reduced with coarse-grain mode; **672,242** installed and reduced successfully (Table 3 lists failure reasons: no main entry point 188,630; non-resolvable dynamic import 128,533; install failure 26,875; non-CommonJS entry point 20,977; others 5,013). They mapped a **snyk.io** vulnerability database (**1,660** vulnerable packages) onto each package's dependency chain and measured how many vulnerable deps Mininode removed (conservatively counting a vuln "removed" only if *all* its source files were removed). Measured quantities: removed files / LLOC / exports, built-in `fs`/`net`/`http`/`https` restriction rates, declared-vs-installed dependency counts, and vulnerability removal.

> **(KO) 코멘트:** 데이터셋 규모가 매우 큼 — npm 전체 1,055,131개 중 672,242개를 실제 설치·축소. 정확성 검증은 별도로 단위 테스트가 있는 37,242개 패키지로 수행. 측정 실험과 검증 실험을 분리한 점이 신뢰도를 높인다.

## 4. Results / Key Findings
**Bloat (§1, §7.2):** only **6.8%** of code-base LLOC is original (93.2% third-party). On average packages **declared 1.9 dependencies but installed 27.3** — roughly **14× more** installed than declared (transitive bloat). After coarse-grain reduction only **9.5%** of all LLOC remained.

**Reduction effectiveness, NPM set (Table 4, 672,242 pkgs):** removed **79.1%** of JS files, **90.5%** of LLOC, **90.4%** of exports. Built-in access restricted: **`fs` 81.7%**, **`net` 92.8%**, **`http` 90.3%**, **`https` 91.3%** of packages.

**Correctness, validation set (Table 1, 37,242 pkgs):** coarse-grain passed **96.0%** of unit tests, fine-grain **95.4%** (1,480 vs 1,711 failures). Fine-grain reduced more aggressively (≈8% more LLOC removed): total removed files 86.9% vs 87.3%, LLOC 85.4% vs 92.2%, exports 86.7% vs 89.0% (coarse vs fine). Built-in restriction on the validation set: **`fs` removed in 28,144 (78.7%) coarse / 28,196 (79.4%) fine**; `net` removed in 33,262 / 34,180 (the latter = **96.2%** of the 35,531 fine-grain passing packages) — these two figures (`fs` 79.4%, `net` 96.2%) are the pair quoted in the abstract.

**Vulnerable dependencies:** **119,433** packages depend on ≥1 vulnerable package — reported as **11.3%** of the 1.05M names in §1's contributions and as **17.8%** of the 672,242 reduced packages in §7.2. Top category is **Prototype Pollution (91,184 packages)**. Mininode removed *at least one* vulnerability from **10,618** packages and **all** vulnerabilities from **2,861** unique packages (≈13.8% partial / 13.65% full removal on average across categories).

> **(KO) 코멘트:** 핵심 수치 — LLOC의 90.5% 제거, `fs` 접근 81.7%·`net` 92.8% 차단(전체 npm 기준), 단위 테스트 통과율 coarse 96.0%/fine 95.4%. 취약 의존성을 가진 패키지 119,433개 중 2,861개에서 모든 취약점을 제거. 취약점을 "찾은" 게 아니라 알려진 취약 의존성을 "제거"했다는 점에 유의.

## 5. How to cite in Related Work
Koishybayev and Kapravelos introduce Mininode, a static-analysis tool that builds a Node.js application's dependency graph from its entry point and removes unreachable code at either file granularity (coarse-grained) or function granularity (fine-grained), additionally enforcing a whitelist of permitted built-in modules via a patched `require` at the Node.js C++ layer [Mininode, RAID 2020]. Measuring 672,242 of 1,055,131 npm packages, they quantify severe code bloat — on average only 6.8% of an application's code is original and packages install ~14× more dependencies than they declare — and show that debloating can restrict access to the `fs` and `net` built-ins in the large majority of applications and strip known-vulnerable transitive dependencies. This establishes that the Node.js substrate underlying many desktop and server applications carries a large, largely *unused* attack surface that can be statically reduced. We adopt their attack-surface framing while [extending it to Electron's renderer/main split / focusing on discovering rather than reducing vulnerabilities].

> **(KO) positioning note:** 이 논문은 **공급망 / 공격 표면 축소(supply-chain & attack-surface)** 각도에서 인용하기 좋다. Electron과의 연결고리는 *간접적이지만 실질적*이다 — Electron 메인 프로세스는 전체 Node.js 런타임(내장 `fs`·`net`·`child_process` 포함)을 그대로 노출하므로, "미사용 내장 모듈 화이트리스트화"와 "미사용 취약 의존성 제거"라는 아이디어가 Electron 메인 프로세스 강화에 그대로 옮겨갈 수 있다. 다만 **취약점 발견(discovery) 논문이 아니라 방어/측정 논문**임을 분명히 해야 한다: nodeIntegration·contextIsolation·preload·IPC 같은 Electron 특유의 위협 표면은 다루지 않으며, 평가 대상도 서버사이드 npm 패키지이지 Electron 앱이 아니다. 따라서 우리 논문에서는 "Electron의 Node 측 공격 표면이 크고 정적으로 축소 가능하다"는 *배경/동기*와 *보완적 방어*로 배치하고, 우리의 기여(취약점 탐지/Electron 특화)와 대비시키는 용도가 적절하다.

## 6. Caveats / what I could not confirm from the text
- **Source:** PDF body text was read from the author mirror (`kapravelos.com/publications/mininode-raid20.pdf`); the USENIX PDF would not render through the fetcher. The USENIX/author abstract and the project page/GitHub README corroborate the headline numbers. Figures/tables were read as linearized text, so a few table cell-to-label alignments (esp. Table 5's per-category partial/full counts beyond the totals quoted) were inferred from surrounding prose, not a clean grid.
- **The 79.4% / 96.2% headline pair** (abstract) reconciles to *validation-set, fine-grain* `fs` (28,196 ≈ 79.4%) and `net` (34,180 ≈ 96.2% of the 35,531 passing packages). The full-NPM numbers are different (`fs` 81.7%, `net` 92.8%, Table 4). I am confident in the values but the abstract does not explicitly state which dataset/mode its two percentages come from; the mapping above is my reconciliation from the tables.
- **119,433 = 11.3% vs 17.8%:** the paper itself reports both — 11.3% against all 1,055,131 names (§1) and 17.8% against the 672,242 successfully reduced packages (§7.2). Not an error on my part; just two different denominators.
- **No Electron-specific evidence.** The paper never evaluates Electron, the renderer process, contextIsolation/nodeIntegration, preload scripts, or IPC. Any claim that its results transfer to Electron is my extrapolation, not stated in the text.
- I did not independently verify the Related Work citations or Table 2 coverage sub-totals beyond what is quoted; the §7 related-work comparison to web/PHP debloating (e.g. Azad et al.) was read but not deeply audited.
