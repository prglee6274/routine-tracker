# Undefined-oriented Programming: Detecting and Chaining Prototype Pollution Gadgets in Node.js Template Engines for Malicious Consequences
**Authors:** Zhengyu Liu, Kecheng An, Yinzhi Cao (Johns Hopkins University)
**Venue / Year:** IEEE Symposium on Security and Privacy (S&P / "Oakland") 2024
**Links:** [paper (IEEE Xplore)](https://ieeexplore.ieee.org/document/10646867/) · [PDF (author-hosted)](https://yinzhicao.org/UoP/UoP-Oakland.pdf) · artifacts: https://anonymous.4open.science/r/UoPF
**Scope tag:** ADJACENT
**Relation to a thesis on discovering Electron-app vulnerabilities (one line):** This is the *second-stage* counterpart to prototype-pollution detection — it automatically discovers and **chains** gadgets that carry a polluted property to an ACE/XSS/FileIO sink, which is exactly the escalation step that turns a renderer-side pollution primitive in an Electron app into main-process code execution once direct gadgets have been patched away.

## 1. Problem, Gap & Hypothesis
Prototype pollution lets an adversary contaminate a property of a prototypical object, altering the victim program's logic (§1). Detecting the *pollution* itself is well studied (Silent Spring, Probe the Proto, ODGEN, and others); the open question the paper attacks is the second stage — **how to actually affect the target program's control- or data-flow to reach a malicious consequence** such as Arbitrary Code Execution (ACE) or File Access Manipulation (Abstract).

The gap: every gadget found by prior work is a **direct gadget**, i.e. the polluted property flows *directly* to a sink without the influence of other polluted properties. Two things make that insufficient (§1): (i) developers have already begun **fixing** direct gadgets, precisely because prior work succeeded in publicizing them; (ii) in some libraries direct gadgets simply **do not exist**, e.g. when gadget-related Node.js standard-library APIs are not used. Hence the need, from an adversary's perspective, for **chained gadgets** — where one gadget alters the control- or data-flow of another gadget, which then reaches the sink. The authors note such chains had previously only been found **manually** (their curated dataset).

Framing/naming: the term **Undefined-oriented Programming** is coined by analogy to **Return-oriented Programming** (binary gadgets chained via `ret`) and to PHP/Java **Object Injection Vulnerability** gadget chains (chained via method polymorphism during deserialization). The distinguishing claim is that JavaScript prototype-pollution gadgets are chained by **undefined properties**, a mechanism unlike ROP or OIV chaining (§1).

Hypothesis: if originally-**undefined** properties are treated as *symbols* in concolic execution, and the set of such symbols is grown incrementally along control-/data-flow dependencies from an initial gadget, then gadget chains can be discovered *and* concretely exploited automatically.

## 2. Methodology
- **UOPF (Undefined-oriented Programming Framework).** The first automated framework to *detect and chain* prototype-pollution gadgets, via **concolic execution of JavaScript with undefined properties as symbols** (§1). One gadget can alter another's control- or data-flow by assigning originally-undefined properties through prototype pollution — hence "undefined-oriented".
- **Two input types, two insights.** Gadget chaining needs (a) **normal program inputs** and (b) **prototype-pollution inputs**. UOPF extracts normal inputs **from the library's own test cases**, selecting those with potential to reach sinks; separately it **gradually extracts additional undefined properties** that have control- or data-flow dependencies on the initial gadget, marks them as symbols, and lets concolic execution be guided toward sinks (§1).
- **Taxonomy of chained gadgets (first of its kind, §2.2).** Two orthogonal axes. By **payload**: *vertically-chained* (one gadget chained with **itself** under different embedded payloads) vs. *horizontally-chained* (two **different** gadgets chained). By **dependency**: *control-flow dependent* (CFD — one gadget changes another's control flow, reaching a sink or a further gadget) vs. *data-flow dependent* (DFD — one gadget **patches errors** introduced into the data flow by the pollution needed for another gadget).
- **Pipeline phases** (Fig. 1, referenced in §5.4): (a) static analysis producing an over-approximated call graph over the target program and its test cases; (b)+(c-2) search over combinations of undefined properties; (b)+(c-1) final **exploit generation** via constraint solving. Every reported gadget is **automatically verified with a generated exploit** — which is why the paper reports zero false positives (§5.3).
- **Target choice.** Node.js **template engines**, deliberately rather than Node.js standard libraries (Silent Spring) or website JavaScript (Probe the Proto), for two reasons (§1): template engines are **less studied** for gadgets, and they are **commonly-used server-side code "just like libc for C/C++ in Return-oriented Programming"**. Template engines also make heavy use of **dynamically generated code**, which defeats the static analysis (CodeQL) that Silent Spring relies on.

## 3. Experiments / Evaluation Setup
Four research questions (§5): RQ1 zero-day gadgets, RQ2 FN/FP vs. state of the art, RQ3 performance, RQ4 code coverage & path number.
- **Dataset curation (§5.1.1), 4 steps — the first Node.js template-engine gadget dataset.** Step I: **40 template engines** taken from the `consolidate.js` repository (an extensive collection of the most widely-used Node.js template engines). Step II: manual search of each engine's **GitHub issues** with keywords `prototype`, `pollution`, `security` → **4 relevant issues**. Step III: manual Google search for **technical blogs** per engine with the same keywords → **9 blog posts**. Step IV: download the corresponding engine version, reproduce and **manually verify** each gadget. Result: **15 known gadgets across 13 template engines** (Table 1), broken down by direct vs. chained and by control-/data-flow dependency. Notably **no known gadget was vertically-chained**, which is why Table 1 omits the vertical/horizontal split.
- **Environment (§5.1.2).** AWS EC2 `c5.12xlarge`: 96 GB RAM, 24-core Intel Xeon Platinum 8275CL @3.00 GHz, 48 vCPUs, Ubuntu 22.04.2 LTS, **Node.js v16.20.0**, configured to run up to **48 concolic-execution worker processes in parallel**.
- **Baselines (§5.1.3).** (1) **Silent Spring (SS)** — original author-provided code, but since it targeted Node.js *standard libraries* the authors **added all Node.js template-engine sinks** (Appendix B, Table 5) to give it a fair shot. (2) **SS-UoPF-init** — Silent Spring additionally seeded with **all undefined properties discovered by UOPF**, because SS only considers direct property lookup by name and misses properties accessed via `for-in` loops.
- **RQ1 run (§5.2).** UOPF executed over the **40 template engines in their latest versions as of February 2023**.
- **RQ2 datasets (§5.3).** Two: **latest template engines with 26 gadgets** and **legacy template engines with 15 gadgets** (the manually curated set). All results manually verified; a TP requires the gadget chain to be **exploitable with prototype-pollution inputs**. Metrics follow prior vulnerability-detection work: FNR = FN/(TP+FN), FPR = FP/(TP+FP), framed as "percentage of missed vulnerabilities" and "percentage of human work sifting reports".
- **RQ3/RQ4.** End-to-end analysis time decomposed into static analysis / gadget search / exploit generation (Fig. 2, log-scale y-axis), and analysis time vs. number of undefined properties (Fig. 3). RQ4 examines new undefined properties, code coverage and unique control-flow paths on **three** selected template engines.

## 4. Results / Key Findings
- **Zero-day gadgets (Abstract):** UOPF detects **25 zero-day gadgets that existing works cannot detect**, of which **13 are chained**; responsibly reported to developers, and **five have already been fixed**.
- **Zero-day gadgets (§5.2 body):** running on the 40 latest template engines, **UOPF reports 21 zero-day gadgets** while **Silent Spring reports only 1** on the same engines → **20 uniquely detectable by UOPF**. (See caveats: the abstract's 25/13 and §5.2's 21/20 do not reconcile in the text I read.)
- **Where the gadgets live (Table 2, 24 enumerated rows).** Affected engines and versions include **node-blade 3.3.1** (7.7K LoC — 6 gadgets, all horizontally-chained, all ACE), **ejs 2.7.4** (3.3K LoC — 3 gadgets, ACE; one *Fixed*), **squirrellyJS 8.0.8** (2 gadgets, ACE, both *Fixed*), **dustjs 3.0.1** (11.2K LoC — XSS), **ect 0.5.9 / coffee-script 1.12.7** (9.6K LoC — ACE), **doT 1.1.3** (ACE and **FileIO**, both *Fixed*), **pug 3.0.2** (5.9K LoC — 2 ACE), **jade 1.11.0** (13.8K LoC — 2 ACE), **hamlet 0.3.3** (2 ACE), **mote 0.2.0** (ACE, where the polluted property name **can be any value** — "ANYKEY"), **ractive.js 1.4.2** (97.4K LoC — ACE), **saker 1.1.1** (XSS). Polluted properties are ordinary-looking names such as `code`, `value`, `line`, `settings`, `escapeFunction`, `client`, `filename`, `inlineMap`, `global`, `destination`, `statics`.
- **FN/FP vs. state of the art (Table 3).** On **latest** template engines: **UOPF TP 26, FN 0, FP 0, FPR 0**; **Silent Spring TP 1, FN 25, FP 4, FNR 0.961*, FPR 0.8**; **SS-UoPF-init TP 2, FN 24, FP 3, FNR 0.923*, FPR 0.6**. On **legacy** template engines: **UOPF TP 10, FN 5, FP 0, FNR 0.333, FPR 0**; **SS TP 1, FN 14, FP 5, FNR 0.943, FPR 0.833**; **SS-UoPF-init TP 4, FN 11, FP 2, FNR 0.886, FPR 0.333**. (*lower bounds estimated from UOPF's results; UOPF's FNR on the latest set is N/A for lack of ground truth.)
- **Why UOPF has zero FPs (§5.3):** it **verifies every gadget with an automatically generated exploit**. Silent Spring's FPs stem from **initial over-tainting** (e.g., in Pug, marking the undefined property `code` as tainted propagates too broadly) and from cases where the injected value is confined to a **string context** (e.g., serialized via `JSON.stringify` before being embedded in a compiled function body), so injected code cannot execute.
- **Why Silent Spring has FNs (§5.3):** four causes — it **only supports direct gadgets** (no chaining), it cannot handle **data-flow dependent** gadgets, its underlying static analysis (**CodeQL**) **cannot process dynamically-generated JavaScript**, and it **misses undefined properties** accessed outside direct name lookup (hence the SS-UoPF-init variant, which only partially closes the gap: 1→2 and 1→4 TPs).
- **Case study 1 — XSS via dynamically generated code (Listing 6, dustjs 3.0.1):** a *direct* gadget where, after compilation, the `render` path looks up the originally-undefined `rootdir` property inside dynamically generated code (lines generated by dustjs at compile time); polluting it flows into the returned value and then into the HTML sent to the client. dustjs HTML-encodes the value, but an adversary can still **inject an `img` tag attribute**. Explicitly noted as a case static analyzers like Silent Spring/CodeQL cannot see, because the relevant lines are generated at runtime.
- **Case study 2 — control-flow dependent chain (ect/coffee-script):** CoffeeScript source is compiled to JavaScript by `coffee-script` and executed with `eval`; two undefined lookups exist — `options.inlineMap` **changes the control flow** such that the second undefined property `options.filename` becomes reachable. Cited as challenging precisely because of the control-flow dependency between gadgets.
- **Performance (§5.4, Figs. 2–3):** static analysis time is **stable and small** relative to concolic execution (the call graph is an over-approximation and the test cases are small); **gadget search dominates** the end-to-end time in most cases, since UOPF tries many combinations of undefined properties; exploit generation is usually small but can spike when many branching statements along the exploitable path force the solver to coordinate multiple properties inside one payload object. End-to-end time grows **roughly linearly** in the number of undefined properties, and since that number stays small, UOPF is claimed scalable even to a large engine (ractive.js at 97.4K LoC being the largest in Table 2).

## 5. How to cite in Related Work
Liu et al. showed that prototype-pollution exploitation does not stop at *direct* gadgets: their **Undefined-oriented Programming Framework (UOPF)** treats originally-undefined properties as symbols in concolic execution and incrementally grows that symbol set along control- and data-flow dependencies, thereby discovering **chained** gadgets in which one gadget rewrites the control- or data-flow of another before a sink is reached [UoP, IEEE S&P '24]. They contribute the first taxonomy of chained gadgets (vertically vs. horizontally chained; control-flow vs. data-flow dependent) and the first curated dataset of Node.js template-engine gadgets (15 known gadgets across 13 engines), and report 25 zero-day gadgets — 13 of them chained — in engines including pug, jade, ejs, dustjs and ractive.js, with consequences spanning arbitrary code execution, file access manipulation and XSS. Because UOPF validates every finding by automatically synthesizing a working exploit, it reports no false positives, whereas the state-of-the-art static detector Silent Spring misses 25 of 26 gadgets on the same targets — largely because CodeQL cannot analyze the dynamically generated code that template engines emit.
