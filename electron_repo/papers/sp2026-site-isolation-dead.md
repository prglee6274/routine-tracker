## 1. Problem, Gap & Hypothesis
Site isolation — giving each site its own renderer process so that a compromised renderer cannot reach another origin's data — is described in the paper as "a cornerstone of modern web browser security." Agentic browsers and extensions break the assumption it rests on: by design an LLM-driven web agent must act *across* origin boundaries (read tab A, call an LLM, act on tab B), so what used to be a rare, low-risk deviation becomes the core execution path. The gap the authors claim: "no previous studies have investigated how agentic browsers implement security mechanisms to protect LLM-driven agent operations from untrusted web content." Their hypothesis is architectural — every system they examined converges on the same pattern (a *privileged background process* that holds user prompts, LLM credentials and storage, versus *untrusted renderer processes*, bridged by IPC channels) — and that this pattern is only as strong as the trust decisions made on incoming IPC messages. The stated security goal they test against: "even if a process rendering a malicious webpage is compromised and gains arbitrary code execution, it should be unable to tamper with the integrity of agent operations."

## 2. Methodology
Three-part, all grounded in source-level analysis of open-source targets:
1. **Architecture analysis.** Manual security-design analysis of two open-source agentic browsers (BrowserOS, Vibe) and seven agentic Chrome extensions, extracting the common process-isolation pattern (Figure 2: renderer + content script = untrusted; background process/task panel + storage = trusted; IPC channel = bridge). Open-source targets were deliberately chosen because "the same level of analysis is considerably more challenging on closed-source browsers."
2. **Two attacks, built on the adversary model "the attacker compromises only the untrusted renderer."**
   - **MPI (Malicious Prompt Injection via IPC):** after gaining arbitrary code execution in the renderer via a memory-corruption bug in the rendering/JS engine, the attacker forges an IPC message that mimics the task panel → background script path. Verbatim Nanobrowser payload: `{'type': 'new_task', 'task': 'Go to gmail.'}`. Because JS-level extension APIs (`chrome.runtime.sendMessage`) are hidden from page scripts, the attacker drops to the **C++-level Mojo IPC objects** beneath those APIs; the forged message is then "indistinguishable from legitimate messages sent by content scripts."
   - **SLI (Stealing LLM-accessible Information):** agentic systems expose a storage interface over IPC to renderers, so a compromised renderer simply issues IPC storage requests and reads LLM conversation history, API keys and user identity.
3. **Defense design + evaluation.** Four guidelines (verify prompt origin; selective, origin-based storage access control; minimize information exposure from the background process; preserve prompt integrity), plus an implemented **guardrail**: cut the direct information flow from webpage content into the *planner*, and have a separate guardrail-LLM classifier check every *navigator*-proposed action for consistency against trusted references (high-level plan, original user prompt, verified action history), emitting a decision label, risk score and rationale.

## 3. Experiments / Evaluation Setup — targets, dataset sizes, configs, what was measured
- **Target set (Table 1), 9 systems.** Browsers: **BrowserOS** v0.28.1 (task automation, 7.4K GitHub stars), **Vibe** v0.1.8 (tab summary, 82 stars). Extensions: **Nanobrowser** v0.1.12 (50K users / 11.3K stars), **Sider** v5.21.1 (6M users), **Eko** v3.1.1 (4.7K stars), **Magical** v3.117.1 (300K users), **WebPilot** v0.10.0730 (40K users), **HARPA AI** v11.4.0 (400K users), **Bardeen** v3.36.0 (200K users).
- **Selection method.** Chrome Web Store searched with the keyword "AI agent" in **October 2025**, taking the first 40 results and discarding non-agentic ones; additionally any extension with **over 4,000 GitHub stars**. For browsers, the two open-source agentic browsers with active commit histories.
- **Feasibility study (real exploit chain).** Each extension installed on **Chromium 130.0.6723.160**; the two browsers rebuilt locally on the same Chromium version. Renderer RCE achieved by chaining **CVE-2025-0291** and **Chromium Issue 379140430**, then forged Mojo IPC messages carried out MPI and SLI.
- **What was measured for the attacks (Table 2).** Per-system success of five MPI consequences (read web content; click buttons; URL navigation; input text; refer agents to chat history) and four SLI consequences (read API key / name / email / chat history). A dash means the system does not support that action at all.
- **Guardrail evaluation (Table 3).** **WebArena** benchmark, **100 randomly sampled tasks** from five of its six open-source websites (those that ran without errors), measuring **task success rate (TSR)**; indirect-prompt-injection resistance measured as **attack success rate (ASR)** using prompts generated by **InjecAgent**, restricted to single-action (URL-navigation) injections because multi-action IPI "consistently fail[ed]". Prompts were additionally hardened to defeat each system's native IPI mitigation (e.g. prepending `</browser-state>` and reopening the tag to escape BrowserOS's XML-tag marking of untrusted content).
- **End-to-end scenarios.** (1) Paper-content exfiltration: BrowserOS signed in to a **test instance of HotCRP** → navigate, click download, open the file URL, summarize the abstract, exfiltrate it in a URL query parameter to the attacker's server. (2) Spear phishing: Nanobrowser + Gmail, SLI to read chat history → MPI to draft, compose and send a tailored phishing email.

## 4. Results / Key Findings — concrete numbers
- **All nine systems are vulnerable.** Every tested agentic browser and extension fell to MPI and/or SLI (Table 2). **WebPilot is the only system not vulnerable to MPI** — and the paper is explicit that this "stems from its limited functionality": it only reads and summarizes web content and exposes no risky actions.
- **Full cross-site control on the most capable targets.** Nanobrowser, Eko and BrowserOS expose *all four* interaction primitives (read content, click, navigate, input text), so the adversary can freely chain them. BrowserOS additionally allows reading cross-tab web content and referring the agent to chat history.
- **No sandbox escape needed.** In the feasibility study "we successfully validated all attack consequences described in Table 2… we were able to perform cross-site operations—effectively bypassing site isolation—without requiring an additional browser sandbox escape vulnerability." In a non-agentic browser the same renderer RCE would require a second, notoriously hard sandbox-escape bug.
- **Two root causes:** (1) no authenticity/origin verification for user prompts arriving over IPC — "the background script blindly trusts internal IPC messages that contain LLM prompts"; (2) unrestricted renderer access to storage, with no origin-based selective access control.
- **Guardrail (Table 3).** BrowserOS: TSR 0.20 → 0.14, **ASR 0.89 → 0.00**. Nanobrowser: TSR 0.27 → 0.29, **ASR 0.52 → 0.00**. Of the 100 blocked IPI attempts against BrowserOS, **85 were prevented simply by removing the untrusted-content→planner flow**; the remaining **15** were caught by the guardrail LLM. Nanobrowser already excludes untrusted content from planning, so its entire 52-point ASR drop is attributable to the guardrail LLM. Cost: a **6% TSR decrease** for BrowserOS, none for Nanobrowser (i.e. no observed guardrail false positives).
- **IPI is a weaker attack vector than MPI/SLI**: IPI ASR varies wildly by target (89% vs 52%) and multi-step IPI scenarios failed outright, whereas MPI/SLI generalize across all systems and execute coordinated multi-step chains.

## 5. How to cite in Related Work
> The renderer-to-privileged-process boundary is the load-bearing security assumption of every multi-process web-derived application, and recent work shows it is routinely mis-implemented. Lee et al. analyze the process-isolation designs of two open-source agentic browsers and seven agentic browser extensions and identify a shared architecture in which a privileged background process holds user prompts, LLM credentials and local storage while untrusted renderer processes are bridged to it by IPC. Because the privileged side performs no origin or authenticity check on incoming IPC messages, an adversary who compromises only a renderer can forge messages at the C++ Mojo IPC layer to inject arbitrary prompts and to read API keys and conversation histories out of local storage — bypassing site isolation entirely, and without the additional sandbox-escape exploit that a non-agentic browser would require. All nine systems studied were vulnerable, and the authors' proposed guardrail reduces indirect-prompt-injection success from 89% to 0% at a 6-point cost in task success rate.

- **"Electron" never appears in the paper** (grep-confirmed over the full retrieved text). The targets are Chromium-based agentic browsers (BrowserOS, Vibe) and Chrome extensions. The ADJACENT tag and all Electron relevance in this note are *my* analytical mapping (Chromium multi-process + privileged background process + IPC bridge ≈ Electron renderer/main + `ipcRenderer`/`ipcMain`), **not a claim the authors make or evaluate**.
- Table 2 was read as flattened PDF text; the per-cell ✓/– assignments above (which system supports which action) are reconstructed from that flattened row order plus the §4.1 "Consequences" prose. Re-verify against the rendered table before quoting any individual cell.
- The MPI attack **presupposes** a renderer memory-corruption bug. The feasibility study uses two known, patched Chromium 130 bugs; the paper does not claim a 0-day renderer exploit, and the attack's real-world prerequisite (a fresh renderer RCE) is not quantified.
- Guardrail TSR values are low in absolute terms (0.20 / 0.27 baseline on WebArena) — these are agent-capability numbers, not defense-quality numbers; the paper does not compare against other WebArena baselines in the portion read.
- IPI evaluation is deliberately restricted to **single-action** injections; the "multi-action IPI consistently fails" claim is stated as an exploratory finding without a supporting table in the portion read.
