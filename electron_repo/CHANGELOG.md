The chain, verbatim from the advisory: `MermaidArtifact.vue` renders diagram content with `mermaidRef.value.innerHTML = props.block.content`, so an `<img onerror=…>` in Mermaid syntax fires **before** the Mermaid library sanitizes → the app hands the renderer **raw `ipcRenderer` as `window.electron`**, and the main process registers a **generic** router `ipcMain.handle('presenter:call', (event, name, method, ...payloads) => …)` allowing *any* method on *any* Presenter class → `McpPresenter.addMcpServer` accepts a config object with an **unvalidated `command`**, and `startServer` runs it via `child_process.spawn`. **Why this changes the argument rather than just adding to it.**

1. **It breaks the profile-only story.** SiYuan (×8) and Notesnook (×2) both escalate through `nodeIntegration:true` + `contextIsolation:false` — an unsafe *`webPreferences` profile*. DeepChat's chain **does not depend on `nodeIntegration` at all**: it goes through a preload-exposed bridge. The corrected framing is **two root-cause families** — (A) unsafe profile, detectable by config auditing (Inspectron); (B) **over-broad IPC surface**, invisible to `webPreferences` inspection and requiring reasoning about what the IPC handlers actually reach.
2. **It is a real-world Message Progression Vulnerability.** renderer DOM sink → `presenter:call` IPC → main-process method → `child_process.spawn` is exactly the MPV class Proton / *Buzz to Boom* defines — field evidence from an app **outside** that paper's 589-app corpus.
3. **A delivery channel the watch has not seen: prompt injection.** Advisory, verbatim: *"Any malicious prompt injection (e.g., from a web search result, a shared conversation, or a malicious model response) can execute arbitrary system commands on the victim's machine."* The untrusted content enters via the **LLM's own output** — a surface neither config auditing, DOM-tree typing, nor network-facing fuzzing models.

**Corrected cross-application taxonomy** (supersedes the two-app note in the Notesnook entry; recorded as `cross_app_note_v2`): **eleven** vendor-published XSS→RCE advisories across **three** independent Electron apps, with **four** escalation primitives — (i) direct DOM sink in the top-level renderer (SiYuan `insertAdjacentHTML`), (ii) same-origin unsandboxed iframe via `contentDocument.write` (Notesnook clipper), (iii) same-origin unsandboxed iframe via `srcdoc` inheriting the parent origin (Notesnook export), (iv) **NEW** renderer→main IPC dispatch into a command-execution gadget (DeepChat). Notesnook (`streetwriters/notesnook`, ~14k stars) is a note-taking app whose Electron desktop client is configured at `apps/desktop/src/main.ts:126` with `nodeIntegration: true`, `contextIsolation: false`, `nodeIntegrationInWorker: true` — and the vendor published **two Critical 9.6 XSS→RCE advisories against that same profile a month apart, through two entirely different feature paths, reported by two different people.**

- **`GHSA-f42f-phvp-43x5` / CVE-2026-33976** — *"RCE via stored XSS in Web Clipper rendering"*, published **25 Mar 2026**, affected Web/Desktop `<3.3.11` (patched 3.3.11) and iOS/Android `<3.3.17` (patched 3.3.17), reporter **`ngocnn97`** — *the same reporter as SiYuan's stored-XSS advisory `GHSA-phhp-9rm9-6gr2`*, i.e. one researcher replaying one technique across two unrelated Electron apps. The clipper's `toAttributes()` (`packages/clipper/src/index.ts`) copies **every** attribute off the source page's `documentElement` with no filtering, so `onload` / `onclick` / `onmouseover` survive into the stored `.clip`; the renderer (`packages/editor/src/extensions/web-clip/component.tsx`) then writes that HTML into a **same-origin, unsandboxed** iframe via `iframe.contentDocument.write(...)`. Payload propagates by **sync** and fires when the clip is opened on desktop.
- **`GHSA-fjm8-jg78-89h4` / CVE-2026-42090** — *"RCE via stored XSS in note export rendering"*, published **25 Apr 2026**, affected Web/Desktop `<3.3.15` (patched 3.3.15) and iOS/Android `<3.3.20` (patched 3.3.20), reporter **`iiihaiii`**. Note `title` / `headline` / `content` are interpolated into the export template **unescaped** (`packages/core/src/utils/templates/html/template.ts:31,33,210,211`), and `exportToPDF()` (`apps/web/src/common/export.ts:40`) sets **`iframe.srcdoc = content` with no `sandbox` attribute**. Advisory, verbatim: *"Because `srcdoc` inherits the parent origin, JavaScript running inside the exported iframe can call: `parent.require("fs")`."* PoC writes `%TEMP%\notesnook-xss-proof.txt` and separately spawns `calc.exe`.

**Why this is worth more than a second anecdote — four uses, all defensible from the advisory text.**

1. **Generality.** The SiYuan series alone could be dismissed as one badly-configured project. Notesnook is an independent codebase, maintainer and reporter exhibiting the identical escalation — enough to state the pattern as a **class**, not a case. The watch now holds **ten vendor-published XSS→RCE advisories across two independent Electron apps**, all against an unchanged `nodeIntegration:true` + `contextIsolation:false` profile.
2. **A second, distinct escalation primitive.** SiYuan escalates through a **direct DOM sink** in the top-level renderer (`insertAdjacentHTML`). Notesnook escalates through **same-origin unsandboxed iframes** — `contentDocument.write` (clipper) and `srcdoc` (export) — where the *missing `sandbox` attribute* is what carries Node privileges into attacker-controlled markup. That is a concrete, checkable predicate (`nodeIntegration && !contextIsolation && iframe without sandbox`) and, critically, **one that `webPreferences`-level auditing such as Inspectron would not by itself flag** — a clean gap argument against config-only analysis.
3. **The same per-sink-patching failure, independently reproduced.** Both fixes are at the sink (escape the template / filter the attributes); the `main.ts:126` profile is described identically in both advisories a month apart. This is the *"fixed at the sink, never at the profile"* dynamic that the SiYuan advisory names verbatim, now observed in a second project.
4. **Import/export and sync as attack surface.** Neither payload arrives over the network at render time — both ride the app's own data flows (clip sync, backup/import, PDF export). These are surfaces a network-facing fuzzer never reaches, and that Proton's message-passing model does not cover either.

**Recorded caveats.** The lead came from a TheHackerWire article and a search summary; **nothing from either is relied on** — every fact above is verbatim from the two GHSA pages. **Not verified:** whether Notesnook has since changed the `main.ts:126` profile (the repo source was not opened; the "unchanged" claim rests only on the April advisory still describing it identically to the March one — **checking current `main.ts` is the obvious next step**); whether further Notesnook advisories exist beyond this pair (no search was run); and note that GHSA-fjm8's Details/PoC section renders inside an unterminated code fence at the source, so its markdown structure is mangled although the substance was readable.

- **`GHSA-phhp-9rm9-6gr2` / CVE-2026-39846** (Critical **9.0**, `CVSS:3.1/AV:N/AC:L/PR:L/UI:R/S:C/C:H/I:H/A:H`, CWE-79 + CWE-94, published **Apr 7 2026**, reporter `ngocnn97`, affected `<=v3.6.3`, patched `v3.6.4`). **Stored** XSS: the table `caption` attribute is saved into the node's IAL properties without escaping, then read back, HTML-**un**escaped, and written into the rendered DOM. Delivery is a crafted **`.sy.zip` note imported into a shared sync target** — the victim is compromised by syncing and opening the note. With `nodeIntegration: true` / `contextIsolation: false`, `<img src=x onerror=require('child_process').exec('calc')>` executes as OS code.
- **`GHSA-6gx2-8gcr-x83f`** (Critical **9.6**, `CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H`, CWE-79 + **CWE-1188 (insecure default)**, published **Jul 13 2026**, reporter Nguyen Van Hiep / `@hypnguyen1209` (MBBank), affected `3.7.1`, patched `v3.7.2`, **no CVE assigned**). **Reflected** XSS→OS RCE via the `siyuan://` deep link, with a file-and-line root-cause chain: `setAsDefaultProtocolClient("siyuan")` (`main.js:81,84`) → the URL is fanned out **with no allowlist or sanitizer** to *every* workspace window via `webContents.send("siyuan-open-url", url)` (`main.js:1692-1696`) → `ipcRenderer.on(SIYUAN_OPEN_URL, …)` (`onGetConfig.ts:168`) → `decodeURIComponent` of the path segment (`uri.ts:107`) → `openBazaarReadme` (`config/index.ts:88-134`) → `showMessage(\`Package not found: ${itemName}\`)` → **`insertAdjacentHTML`** (`message.ts:73,84`, plus sinks at 44-51 and 59).

**Why this is worth more than a motivating anecdote — three uses, all defensible from the advisory text.**

1. **The profile, stated by the vendor.** Every `BrowserWindow` runs `nodeIntegration:true, webviewTag:true, webSecurity:false, contextIsolation:false`, with `@electron/remote` global, `--disable-web-security` on the command line (`main.js:87`), and `content-security-policy` / `x-frame-options` / `access-control-allow-origin` **stripped from every response** (`main.js:554-565`). The advisory's own summary: *"There is no CSP, no SOP, no origin isolation."*
2. **The recurrence curve.** The advisory names **seven prior XSS-to-RCE advisories against the identical profile** (`GHSA-pcjq-j3mq-jv5j`, `-27qc-m5gf-jv5r`, `-mvjr-vv3c-w4qv`, `-ff66-236v-p4fg`, `-phhp-9rm9-6gr2`, `-grjj-6f6g-cq8q`, `-2h64-c999-c9r6`) and states, verbatim: ***"Each has been fixed at the sink, never at the profile."*** It adds that `showMessage` is the shared sink for **~20 sibling reflection paths**, so a per-call escape leaves the siblings live. That is direct empirical support — from the affected project, not from a paper's motivation section — for the claim that **per-sink patching does not close the class while the `webPreferences` profile is unsafe**, which is precisely the argument for tooling that audits the *profile* (Inspectron) or defends the *escalation* (COINDEF) instead of individual sinks.
3. **A field instance of message progression.** The deep-link path is *OS protocol handler → main process → unsanitized broadcast over renderer IPC → DOM sink → Node API*, i.e. a real, shipped, cross-process chain of exactly the shape **Proton / "Buzz to Boom"** defines as an MPV. It also composes: chaining `GHSA-cvhv-7xhj-xjp8` (unauthenticated workspace write) flips `Conf.Bazaar.Trust=true` on disk and removes the last non-default prerequisite, making the whole thing **zero-configuration and single-click**.

The advisory's recommended fix doubles as a clean statement of the secure baseline to measure real apps against: `contextIsolation:true, sandbox:true, nodeIntegration:false, webSecurity:true`, a `contextBridge` preload exposing only the required Node subset, and deletion of both `--disable-web-security` and the header-strip block. This entry is the **application-level counterpart** to the existing upstream-Electron CVE context entry, which covers the framework's own bugs — together they now cover both sides of the boundary.
