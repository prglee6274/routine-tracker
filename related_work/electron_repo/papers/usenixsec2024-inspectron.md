## 1. Problem, Gap & Hypothesis
Electron apps fuse Chromium + Node.js into standalone desktop apps. Many browser-baked security protections (Same-Origin Policy, sandboxing, CSP, permission prompts) become *optional, developer-configurable* settings in Electron, and prior work shows developers struggle to configure security mechanisms correctly (§1). Because apps ship a *static* copy of Chromium/Node.js, they also lag upstream security patches, creating exploit windows (§1). The stated gap: existing aids are either static (e.g., Electronegativity) or defenses against specific attack classes; there is "a clear necessity for a system that is both dynamic and automated" that can investigate a more comprehensive range of failure scenarios (§1). Inspectron's threat model (§2.1) was derived empirically by examining 50+ vulnerability reports filed against Electron apps over ~7 years, and considers an attacker who is either another app user or a malicious third-party component (script/iframe/webview/navigated page). The implicit hypothesis: insecure practices are not isolated incidents but an ecosystem-wide problem detectable at runtime without source code.
(KO) 핵심 갭은 "동적 + 자동화 + 포괄적"인 도구의 부재다. Electronegativity 같은 정적 분석은 런타임 설정값(예: 난독화된 `nodeIntegration: !0`)을 놓친다는 점이 동기. 위협 모델은 7년치 실제 취약점 리포트 50건+ 분석에서 도출됨.

## 2. Methodology
Inspectron is an automated **dynamic, black-box** framework requiring no source code (§3). Workflow (Fig. 3): (1) **Packaged app** — mount the distributable, extract the `resources` directory, locate the binary, and run it as a Node.js process via the `ELECTRON_RUN_AS_NODE` flag to read `process.versions` (Node/V8 versions). (2) **Instrumented Electron** — because Electron has a different ABI than Node.js, app code must run against an Electron binary with a matching Node module version; the authors instrument specific TypeScript and C++ functions in the Electron source and rebuild it, so calls emit the status of variables/arguments. (3) **Puppeteer script** — each app is launched on the instrumented Electron with a remote debugging port; a Puppeteer client performs renderer-side checks (collects `contextBridge`-exposed APIs via a global `window.reportExposedAPIs`, parses the Chrome version, intercepts network requests, captures CSP *after* developer modification of response headers). (4) **Additional (no-run) checks** — CSP evaluated with Google's CSP Evaluator; reachable domains visited with XSStrike to flag WAFs and DOM XSS; Electron fuse checks (e.g., cookie encryption). (5) **Report** — results merged into a single parsable report flagging insecure practices (explicitly *not* proof of exploitability). Inspectron audits **16 classes of misconfigurations**, including 12 security-related webPreferences and 33 command-line switches; it covers 5 attack vectors not handled by Electronegativity.
(KO) "계기화된 Electron 재컴파일 + Puppeteer 원격 디버깅" 조합이 핵심 메커니즘. 보고서는 '비보안 관행(insecure practices)'을 표시할 뿐 실제 익스플로잇 가능성을 증명하지 않는다는 점을 저자들이 명시(§4 용어 정의).

## 3. Experiments / Evaluation Setup
- **Electron dataset (instrumented builds):** Built **24 instrumented Electron versions** (v14–v24 for Linux, v12–v24 for MacOS); could not build Linux Electron < v13 due to unavailable Debian build files (§4, "Electron Dataset").
- **App dataset funnel:** Manually inspected **282** apps on Electron's official showcase → downloaded **167** (after filtering unavailable/discontinued/Linux-or-MacOS-incompatible/paid) → retained **109** apps for which a matching instrumented Electron build existed; these 109 are the main analysis set (§4, "App Dataset").
- **Deeper study:** **10 popular apps** examined in more depth, adding pre-recorded **user-interaction traces** (sign-in, open/close tabs, text input, file upload, link clicks) to raise coverage, plus historical-version tracking and PoC exploits for 3 V8/Blink CVEs (§4, "Popular apps").
- **What they measured:** per-check counts of apps exhibiting insecure practices (webPreferences, navigation handling, IPC sender verification, CSP, cookie encryption, permission handling, certificate verification, openExternal, custom protocols, etc.), plus a head-to-head against Electronegativity on the same dataset under a "one-touch" (open-but-no-interaction) protocol (§4.1).
- **Validation/FP:** For the 109-app set, the authors manually verified every detection and report **zero false positives** (§4, "False Positives").

## 4. Results / Key Findings
Insecure webPreferences across the 109 apps (Table 1): **nodeIntegration = true in 49** (renderer gets full Node.js access → can `require` modules and run shell commands), **contextIsolation disabled in 54** (exposes preload↔renderer to prototype-pollution-style takeover), **sandbox disabled in 64**, **webSecurity (SOP) disabled in 8**, allowRunningInsecureContent in 6, disablePopups false (popups allowed) in 64, WebSQL enabled in 81, JavaScript enabled in 83, webviewTag enabled in 15. The 64 unsandboxed apps reflect that sandbox-by-default only arrived in Electron v20 (Aug 2022) while most apps run older versions (nodeIntegration secured by default since v5, contextIsolation since v12).
- **WebViews:** of 15 apps using WebViews, only **4** enforce preference limits on attach.
- **Navigation handling:** of 109 apps, only **24** implemented navigation limits; only **32** prevented arbitrary content in new windows; only **23** used the modern `setWindowOpenHandler()` while **11** still relied on the deprecated `new-window` event.
- **IPC:** **43** apps set up custom IPC channels to the renderer, but only **13** implemented sender verification — leaving **30** apps where a compromised renderer can trigger IPC unchecked.
- **Preloaded APIs:** **19** apps exposed extra functionality via `contextBridge`; **7** of those lacked context isolation (prototype-pollution risk on the preload script).
- **CSP:** only **18** of 109 apps implemented a CSP; **16** of those returned warnings from CSP Evaluator (15 with a medium-severity directive). 
- **Cookie encryption:** only **2** apps (Front, Slack) encrypted on-disk cookies; the rest stored cookies in plaintext, and **66** apps were found storing sensitive/auth information.
- **Custom protocols:** **36** apps register custom protocols; only **4** account for them in navigation decisions. **Certificate verification** overridden in **8** apps; **openExternal** used in **56** apps, with **none** of the inspected navigation handlers performing extra URL sanitization before passing to the OS shell.
- **Patch lag / CVE trickle-down:** apps depend on Electron versions up to 4 years old; latest Wordpress, Postman, WhatsApp desktop apps confirmed vulnerable to V8/Blink RCE-class CVEs (CVE-2021-30632, CVE-2022-1364, CVE-2022-3656) up to ~2 years old (Table 2).
- **Vs. Electronegativity (Table 4):** Inspectron reports **482 total true positives vs. 440** for Electronegativity; e.g., insecure webPreferences in 66 apps vs. Electronegativity's 23 true positives; experimental command-line features in 10 vs. 5. Electronegativity has coverage advantages on event-triggered checks (it scans all source), but produces false positives Inspectron avoids by observing runtime behavior.
- **New framework bugs:** two incorrect Electron implementations of web standards reported to the Electron team — `Permissions-Policy` failing to block screen access via `getUserMedia()`, and `<webview>` ignoring `X-Frame-Options: DENY` (Electron called the latter "expected and desired behavior").
- **Disclosure outcomes (§5 Ethics):** reported to 4 popular apps (June 2023), then to **100** additional apps; **43** vendors responded and **11** deployed fixes; rewards from Postman, Wordpress, Cacher; the Altair GraphQL report was rated a **"High Severity" CVE by NIST** (CVE-2024-54147 per secondary sources) and GitHub issued an advisory; 2 reports filed to the Electron framework itself. Vulnerabilities were found in 4 apps among the deep-dive set.

## 5. How to cite in Related Work
Ali et al. introduced Inspectron, a dynamic black-box auditing framework that runs packaged Electron applications on instrumented builds of the framework to detect 16 classes of security misconfigurations without source-code access [Inspectron, USENIX Sec '24]. Auditing 109 apps, they found pervasive deviations from Electron's recommended practices — e.g., 49 apps enabling full `nodeIntegration` in the renderer, 64 disabling the sandbox, and only 13 of 43 apps verifying IPC senders — and showed their dynamic approach yields more true positives (482 vs. 440) and fewer false positives than the static state-of-the-art tool Electronegativity. They further demonstrated that stale bundled Chromium/V8 leaves popular apps exposed to known RCE-class CVEs long after upstream patches, and disclosed flaws to 100+ vendors plus two web-standard implementation bugs to Electron itself.
