# COINDEF: A Comprehensive Code Injection Defense for the Electron Framework

**Authors:** Zheng Yang; Simon P. Chung; Jizhou Chen; Runze Zhang; Brendan Saltaformaggio; Wenke Lee (Georgia Institute of Technology)
**Venue / Year:** 2025 IEEE Symposium on Security and Privacy (S&P / Oakland)

**Relation to a thesis on discovering Electron-app vulnerabilities (one line):** The most recent comprehensive Electron *defense*; it consolidates a 20-app vulnerability/exploit corpus (largely overlapping the NDSS 2023 set, now annotated with CVEs and full RCE kill chains) and directly benchmarks against the NDSS 2023 DOM-tree work ("DOMTYPING"), making it the key contrast point and a ready source of attack vectors for a discovery thesis.

## 1. Problem, Gap & Hypothesis

Electron fuses web and native environments in one executable, so web vulnerabilities (XSS, prototype pollution, client-side-redirect) can reach the client machine and escalate to remote code execution (RCE) — illustrated by the 2022 *Water Labbu* campaign against Meiqia (an Electron chat app used by 400,000+ companies) that exploited CVE-2021-21220 and stole >$300,000 in cryptocurrency (§1). The gap: prior defenses are siloed — web XSS defenses and NodeJS RCE defenses each work only in their own runtime and cannot operate across Electron's *dual* (web + native) environments simultaneously; and recent Electron-specific studies addressed symptoms or misconfigurations, **not the root cause: code injection** (§1, §7). Building on Su & Wasserman's insight that a successful injection must change a program's intended syntactic structure (ref [23]), the authors form two hypotheses (§1): (1) any code-injection attack ultimately yields a structurally different **AST**; (2) Electron's **JavaScript engine** is the single choke point where both web and native code can be protected at once. Hence: enforce **AST structural integrity with execution context** inside the V8 interpreter.

> (KO) 갭은 "웹 방어 따로, 네이티브 방어 따로"라서 두 환경이 융합된 Electron을 동시에 못 막는다는 점, 그리고 기존 Electron 연구가 *근본 원인(코드 인젝션)* 이 아니라 증상/오설정만 다뤘다는 점. 가설: 인젝션은 결국 AST 구조를 바꾼다 + JS 엔진(V8)이 웹·네이티브 코드가 모두 지나가는 유일한 chokepoint. 따라서 엔진 내부에서 AST 구조 무결성을 강제.

## 2. Methodology

COINDEF runs **inside V8** in two phases (§3):

**AST Structural Signature (§3.3.1).** For every function, COINDEF extracts each AST node's type, value, and position. To allow legitimate runtime input variation, it replaces concrete values of *data nodes* (literal, name, key, certain `value` nodes, and a `variable proxy` only when not under a `call`/`new`/`assign`) with placeholders (Table 1). The worked example `eval(\`cl.${color}()\`)`: legitimate `color=red` yields one signature; an injected `red();exec('cmd')//` produces extra `call`/`var(exec)`/`literal` nodes and is rejected (Fig. 4). This catches both function invocations and *standalone* injected code (not just function-related ops).

**Execution Context Annotation (§3.3.2).** To defeat *mimicry attacks*, each profile is isolated per process — `MainProcess`, `BrowserWindow`, `SubFrames` — and annotated with caller info and eval call-site location (Fig. 5). Profiles are split into **Static** (from local script files; immutable, lazily-compiled functions still counted static) and **Dynamic** (from dynamic-code APIs — `eval`, `document.write`, EventHandlers, `importScript`, script-includes — using CodeQL's injection-sink definitions).

**Hybrid profiling (§3.4).** Static profiling uses a customized **d8** (V8 shell) with lazy compilation disabled to build a *complete* set `PS` of all functions in the app's files. Dynamic profiling exercises the app semi-automatically (crawler clicking buttons/menus/typing, plus manual exercises from user manuals and end-to-end tests if available) to add contextual `PD`. Profiling is at **function-level granularity**; an invalid function is replaced by a returned **noop function**, otherwise the original.

**Runtime enforcement (§3.5, Alg. 1).** Since `PS` is complete, the only "unlearned" runtime profiles are dynamic (`U = RD − PD`). Static profiles are checked by URL+callsite; dynamic by URL+caller+callsite. Unlearned profiles fall to **security policies**: local-dataflow code is always allowed; in `MainProcess` unknown code is rejected (zero-trust); in `BrowserWindow` cross-origin is rejected and same-origin gated by `SameOriginInBrowser` (default false); in `SubFrames` everything is rejected unless `SubFrame` enabled (default false) and origin is in the allow-list. Two modes: **security-first** (default) and **usability-first**. §3.6 formalizes a recursive `Match(Tmodel, Truntime)` over data/exec/intermediate node types (data nodes match on type; exec nodes must match exactly; intermediate nodes recurse on children).

**Implementation (§3.7):** instrumentation hooks in V8's interpreter (base `AstVisitor`, plus script/parser info and call-stack) and Electron's web-frame delegates / V8 `Isolate` for process annotation. **< 150 LoC in V8 + 500+ LoC in two self-contained C++ files**; it does **not** profile internal NodeJS/Electron functions; it does not require human-readable code (works on minified/bundled/obfuscated production builds).

> (KO) 방법론 핵심 3가지: (1) AST에서 *데이터 노드만* 값 변동을 허용(placeholder)하고 exec/구조 노드는 정확히 일치해야 함 → 인젝션은 반드시 새 노드를 만들어 차단됨. (2) 프로세스별(Main/BrowserWindow/SubFrame) + caller/callsite 컨텍스트를 붙여 mimicry 공격 방지. (3) 정적 프로파일링(d8, lazy compilation off)이 함수 전체를 *완전히* 커버하므로 런타임 미학습은 동적 코드뿐 → 보안 정책으로 처리. 파서가 파싱하는 김에 프로파일을 만들어("free ride") 사용자 상호작용 중 오버헤드 0을 노림.

## 3. Experiments / Evaluation Setup

Evaluated on **20 real-world Electron apps** vulnerable to code injection/RCE (Table 2), sourced from the GitHub Advisory Database, articles, and blogs. Apps span scale and category: MSTeams, Slack, Discord, VSCode, Joplin, Boostnote, Simplenote, Altair-graphql, Appium-desktop, BlockBench, electron-crud, arc-electron (Advanced REST Client), vmd, antares-sql, Markdownify, Poddycast, OhHai Browser, Jukeboks, GraSSHopper, ARDM — many overlapping the NDSS 2023 set, now tagged with attack vectors (template injection, markdown preview, client-side-redirect, prototype pollution, reflected/stored/DOM-based XSS) and Electron versions (v7–v19). All tests use the **vulnerable versions**, so attacks are effectively 0-day relative to COINDEF (it is agnostic to the vectors). Payloads were confirmed-working and modified to log a compromise indicator instead of causing harm; messages were injected via an MITM proxy, DB records via a crafted MySQL row, markdown via crafted files. Research questions RQ1–RQ4 cover effectiveness, FP/FN impact, overhead, and comparison to SOTA. Code coverage during enforcement was measured at **function level on first-party code** (ground truth from the Acorn parser). Performance ran on Ubuntu 22.04, Intel E5-2680v3 @2.50GHz, 64GB RAM; page-load overhead via `navigationStart`→`loadEventEnd` (median of 10 runs); interaction overhead via **Speedometer 2.0** (17 TodoMVC apps, 100 add/complete/remove items, 10 runs). SOTA comparison (§4.3) used Discord, Jukeboks, and a custom **AllinOne** app (11 injection points → 10 RCE) against **SYNODE, XGUARD, and DOMTYPING** (the NDSS 2023 DOM-tree work).

> (KO) 대상 20개는 NDSS 2023 세트와 상당 부분 겹치되 CVE/공격벡터/Electron 버전이 부착됨 → *발견 논제용 공격 코퍼스로 매우 유용*. 모든 평가는 취약 버전에서 0-day로 수행. 비교는 SYNODE/XGUARD/DOMTYPING과 직접 수행(맞춤형 AllinOne 앱 포함).

## 4. Results / Key Findings

- **Effectiveness (Table 4):** across 20 apps, **79 attacks** executed (2–8 per app; e.g., 6 against Discord forming two 3-step kill chains). In **security-first** mode COINDEF **blocked all code-injection attempts** with **0 false negatives**; in **usability-first** mode 2 injections bypassed in 2 apps but **RCE was still prevented in all cases (0 RCE FN)**.
- **False positives:** **17 FPs in security-first across 3 of 20 apps**; **0 FPs in usability-first**. 12 FPs were Slack/Discord "In-App View" features (video/file preview in SubFrames, disabled by default); 5 were VSCode extension updates adding new script files (fixable by re-running learning mode). Impact judged minimal (Fig. 7: blocked video still openable in external browser).
- **Overhead (RQ3):** average **3.96% one-time startup (page-load) overhead** (Table 4); highest 9.31% for Slack (just 19 ms absolute), lowest 1.04% for Poddycast; higher for network-loading apps (Discord's first page = 57 scripts → 20,000+ AST profiles validated). **User-interaction overhead negligible** (Table 5: Speedometer median 116.9 ms baseline vs 116.9 ms COINDEF; max ~1.78%); authors statistically conclude the two distributions are the same — no interaction overhead by design (no hooks in function calls). Storage grows linearly; largest (Discord) is 2 MB on disk / 10 MB in memory.
- **Learning effort (Table 3):** converged AST profiles took ~4 hours for complex apps, ~30 min for simple ones (≈0.1 h with automated e2e tests for VSCode/Joplin/SimpleNote). 18/20 apps run dynamic code; only the 3 collaboration apps + VSCode have dynamic code in SubFrames. Function-level enforcement coverage averaged **87.03%** (3 apps at 100%, 5 over 90%, 12 over 75%).
- **Comparison to SOTA (Table 6, §4.3):** Over the comparison set (14 code-injection attacks → 12 RCE), **SYNODE** missed 10 injections (8 → RCE) and had 2 FPs; **DOMTYPING (NDSS 2023)** missed 9 injections (7 → RCE) and had 2 FPs — because it does **not** handle *client-side-redirect* or *dynamic code execution* (`eval`); **XGUARD** blocked all RCE but missed all 14 code injections (attacks reach critical stages first) and had 2 FPs from minified-code call-chain modeling. **COINDEF: 2 code-injection "misses" but 0 RCE and 0 FN in security-first** — claimed as the only complete protection. The Discord case study (Fig. 8) shows COINDEF blocking the kill chain at the client-side-redirect step, and even if bypassed, blocking the prototype-pollution step (overwriting `RegExp.prototype.test` / `Array.prototype.join` creates new AST profiles absent from `BrowserWindow`).
- **Robustness (§5):** blocked all 20 cited attacks + 59 evasion variants.

> (KO) 숫자 요약: 20앱·79공격 전부 차단(security-first FN 0), FP 17건(전부 SubFrame/확장 업데이트, usability-first에선 0), 시작 오버헤드 평균 3.96%, 상호작용 오버헤드 ≈0. 비교에서 DOMTYPING은 client-side-redirect와 동적 코드 실행(eval)을 못 막아 9건(→RCE 7건) 통과 — 이게 COINDEF가 강조하는 차별점.

## 5. How to cite in Related Work

> Yang et al. (IEEE S&P 2025) propose COINDEF, the first defense to tackle the *root cause* of Electron RCE — code injection — across both the web and native environments by enforcing AST structural integrity, annotated with per-process execution context, inside the V8 interpreter. Using hybrid (static + dynamic) profiling at function granularity, COINDEF blocked all exploits across 20 vulnerable real-world apps (including Slack, Microsoft Teams, Discord, and VS Code) with an average 3.96% startup overhead and negligible interaction overhead. They show that prior Electron defenses leave gaps: the DOM-tree-type method of Jin et al. (NDSS 2023, "DOMTYPING") misses client-side-redirect and dynamic `eval`-based execution, while XGUARD blocks final RCE but not the intervening code injections.

> (KO) 포지셔닝: 발견(discovery) 중심 논제에서 COINDEF는 *대조군 방어*이자 *공격 코퍼스의 출처*다. 직접적 동기 부여보다는, "최신 방어가 어디까지 막고 어디서 실패하는가"의 기준선. 활용 포인트: (1) COINDEF가 명시적으로 *범위 밖(out of scope)* 으로 둔 영역 — 의도적으로 임의 입력을 실행하는 앱, 소프트웨어 공급망 공격, 직접적 command injection(`exec`로의 데이터 인젝션, §6) — 은 *새 취약점 발견 논제가 노릴 빈틈*이다. (2) COINDEF 자체가 dynamic profiling 커버리지(평균 87%)에 의존하므로, 미학습 경로/SubFrame 우회는 발견 연구의 표적이 될 수 있다. (3) 20앱 CVE/공격벡터 표(Table 2)는 재현·확장용 데이터셋으로 인용 가능.

## 6. Caveats / what I could not confirm from the text

- I read the full body (§1–§9) and all tables/figures captions present in the extracted text. Reference list entries beyond ref [23] (Su & Wasserman) and the cited CVEs were only partially in the extracted text (truncated mid-references); I did not enumerate every citation.
- "DOMTYPING" in this paper = the NDSS 2023 DOM-tree-type work (Jin et al., their ref [21]). The two papers share a first-author surname "Jin" but are **different first authors** (Zihao Jin in NDSS 2023; "Jin et al." cited via ref [21] here) — confirmed by context, but I could not see the full ref [21] string to verify author list character-for-character.
- The "79 attacks" total: I summed Table 4's per-app counts implicitly; the text states "a total of 79 attacks across 20 applications" (§4.1.4) — confirmed in prose.
- The exact definition/derivation of the 3.96% mean and 87.03% mean coverage are taken from Table 4's stated "Mean" row; I did not recompute from raw per-app values.
- Whether COINDEF was *also* run against the full 20-app set in the head-to-head SOTA table is not the case — the §4.3 comparison uses only Discord + Jukeboks + the custom AllinOne app (14 injections / 12 RCE); the 79-attack/20-app result is COINDEF-only (§4.1).
- Hardware/OS and Speedometer numbers are quoted directly; I could not independently reproduce them.
